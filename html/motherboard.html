CONVERGING MIRROR
routing bus · RAM ⇄ NB
Design choices: one hub — the north bridge is the agent client: the code CLI you run (pi.dev · Claude Code · crush CLI). It is the local harness between the LLM and this machine — classic north-bridge topology: the CPU (an API call) hangs off the NB and gets everything through it; RAM hangs off the NB too (the memory controller lives there), so there is no direct CPU ⇄ RAM bus — the client feeds the CPU, reaches the tools in RAM, and pages the drive. L3 is the provider cache — a real cache between CPU and RAM, caching the session working set; the drive files are the source, never a "cache layer". The violet routing lines carry the working set (CPU ⇄ NB) and session + tools (NB ⇄ RAM); the orange storage line pages the drive. No south bridge, no execution — and no context assembly in the NB: that is the linker's job, and it lives in RAM. RAM holds every running instance, stacked vertically: the linker (mwp-tool — context assembly), the chat session, the JigsawFlow microkernel (a daemon — an instance like any other program), and the tools (CLI · MCPs · python/node), loaded from the drive into RAM where they run — exactly how a real OS loads executables from disk into memory. The monitor shows RAM. Every bus is two lines, dots flowing one way each.
